# 100x Customer Catalog Discovery & Multi-Lifecycle Radius Fortress

## 1. Full-Catalog Discovery & Pagination Integrity in Popular in Your Area
1. **Dynamic Pagination over Static Previews**: In `AllListingsPage` (`lib/pages/customer/all_listings_page.dart`), the page must never assume `widget.shops` is the complete shop list. It must query `get_nearby_shops` using `LocationProvider.currentLocation` and `DeliveryCalculator.maxRadiusKm` to resolve all active shops in the delivery radius, query the exact total product count in Supabase, and paginate dynamically until exhaustion (`_hasMore = false`).
2. **Never Truncate "See More" Prematurely**: When a customer taps "Load more products" in `AllListingsPage`, the button must not disappear when `displayLimit >= currentLength`. If `_hasMore` is true, it must fetch the next batch from the database, increment `_displayLimit`, and only render the end-of-list marker (`"You've reached the end of popular items in your area 🛍️"`) once all matching products across all active shops in the delivery radius have been loaded.
3. **True Total Counter Accuracy**: The product counter in `AllListingsPage` (`$totalCount products`) must dynamically reflect the true total number of active products in the delivery radius (or the exact filtered match count when searching/filtering), rather than reflecting a preview sample.
4. **No Artificial Per-Shop Product Ceilings**: In `CategoryProductsPage` (`lib/pages/customer/category_products_page.dart`), never arbitrarily cap products from nearby shops using `take(5)` or low limits. All products belonging to active shops within the delivery radius must be presented.

## 2. Multi-Lifecycle Radius Compliance (Admin, Customer, Rider, Seller)
1. **Admin Radius Source of Truth**: All delivery radius evaluations across customer listings, category pages, search, and checkout MUST derive from `DeliveryCalculator.maxRadiusKm`, which dynamically mirrors `PlatformConfigProvider.instance.maxDeliveryRadiusKm` (loaded from `platform_config`).
2. **PostGIS SQL RPC Safeguards**: `get_nearby_shops` and `search_shops_geospatial` SQL RPCs must clamp `p_radius_km := LEAST(p_radius_km, v_admin_max_radius)` where `v_admin_max_radius` is read from `public.platform_config`, ensuring database-level enforcement of the admin's delivery radius.
3. **Customer Search Radius Fortress**: In `HomePage._searchShops`, `shopResults`, `addProducts`, and shop cross-links must strictly verify `DeliveryCalculator.isWithinRange(d)` on all candidate stores and products, preventing search leaks.
4. **Category Products Radius Fortress**: In `CategoryProductsPage`, every product loaded must belong to a shop verified with `DeliveryCalculator.isWithinRange(d)` based on the customer's location.
5. **Rider GPS Lock & Zero-Leak Notification Radius**: In `DeliveryDashboardPage` (`lib/pages/delivery/dashboard_page.dart`), if rider GPS coordinates are null (`_riderLat == null || _riderLng == null`), `available` orders MUST remain empty (`[]`). In `get_nearby_unassigned_orders` RPC (`20290000000148_100x_geospatial_radius_and_discovery_fortress.sql`), null rider coordinates immediately `RETURN;` (empty). In addition, all candidate orders are client-side filtered with `_pickupDistKm(o) <= _maxRadiusKm`, completely eliminating false audio alarms (`BellAlertService`) for out-of-range orders.
6. **Soft-Delete Inviolability**: Every query against the `products` table for catalog exhaustion or search MUST strictly include `.eq('is_deleted', false)` per core project rules.
